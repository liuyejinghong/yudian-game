# 两线并行验证：美术与技术

2026-10-03｜v0.4｜状态：**工作包定义；实际游戏执行 NOT_RUN。**

所有者认可两线并行。两线用同一个产品场景与最新决定，不各做一套游戏，不复制两套计划／资源事实。每个执行批次先确定范围、依赖、文件归属、费用和设备；文档不是整款游戏的自动开工许可。

## 共同场景

小型基地含三类机器人、太阳能、加工与仓储／充电／维修能力；一块需要清场整平的土坡、一处可开挖矿点。玩家提出缺料建设目标，系统补齐前置，施工留下地形变化，机器人轮换补能与维护，最终设施工作并能保存恢复。

增加平稳环境和天气增耗对照；分别验证零电与零耐久原地停机、合适机器人送回维修、救援者自身返程预算。常态约 10% 回充不保证恶劣环境必定安全。

测试档可预置阶段能力用于定位验证，但正式新档仍需由玩家建基地。所有数量、耗时与资源均以具名 fixture 固定，不能为某条线临时改成无限资源。

## A 线：美术小样

输入：[美术方向](../art/art-direction.md)、[返航与救援](../product/energy-return-and-rescue.md) 与共同场景。

交付：同场景原创风格候选；同位置改造前后图；选中后的一台机器人、两类设施、坡地与矿点状态小样；实际镜头与正常缩放下的可读性记录。最新停机原因、拖运与维修状态需要可区分，不用台词替代行为。

不得：重新提出已淘汰的像素／军事风默认；用海报替代场景；把模型图片称为完成网格；未经许可下载／复制商业游戏资产；仅凭概念图签资源生产标准。

通过点：所有者认可视觉方向，且关键对象、作业、地表变化与维护状态在小样里可读。

## T 线：技术证据

输入：[技术计划](../engineering/technical-validation-plan.md)、[超分专项](../engineering/upscaling-and-renderer-evaluation.md) 与同一场景，灰模可先行。

交付：精确版本与原生依赖记录；可启动 Mac 构建；真实目标链；局部地形改造、导航、健康、救援与存档验证；本地规划／模型对照；参考机与较低配置数据；原生和可用超分模式的同条件画质／性能；一个有证据的主推荐和剩余风险。

不得：用 Linux／headless 替代 Metal 实测；只有移动图标没有工作；关掉 AI 或真实地形后声称本地低配通过；以开发机 36GB 当商业下限；模型坏结果被挡住即计作目标成功；用生成帧数掩盖基础帧率或模拟降速。

## 汇合闸门

A 的真实资源放进 T 的同一工程；任务、地表、天气增耗、回充、停机救援、维修、本地推理与保存一起运行。记录画面与状态、帧时间分位、规划延迟、内存压力、模拟实际倍速和地形更新峰值。

只有完成这个交叉验证后才冻结美术生产标准和主引擎配置。不能用两份各自漂亮的单独报告拼出“联合通过”。

未通过时先定位原因，给出资源／算法／配置调整；不得自动砍掉地表改造、机群保障或本地完整体验。产品级降范围由所有者决定。
