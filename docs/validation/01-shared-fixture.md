## P0：开工前唯一写者登记

Codex 主控创建 `validation/shared/`：场景清单、内容版本、目标/授权、起始库存、设备状态、地图和相机、随机种子、观察权限、事件时点、质量档及输入动作序列。推荐 JSON 数据，具体 schema 由主控写一次，A/T 不各自定义。

登记精确提交与 fixture hash。后续改动必须升 fixture 修订并使相关成绩过期；不因一种算法失败就给它单独增加资源。共同约定是目标、任务、设备、区域和内容的稳定 ID，不把图片名、Godot NodePath 或模型回复字符串当资产身份。

## S：最小场景

- 12 台机器人：4 驮运、5 筑垒、3 望山。只一台驮运配置本试验拖运附件；载荷与能源限制显式记录。数量借作测试规模，不强制正式新档相同。
- 6 个已有设施对象：着陆器、太阳能、仓储、加工、充电、维修。目标是在另一块获准地块建成第 2 个阵列。已有设施用于隔离验证，不代表正式开局全部预建。
- 约 200×200 米的局部地图，逻辑格候选 2 米；一个可整平的坡地块、一处铁矿、一处铜矿、两条可选返程路线。尺寸仅为初始候选；引擎坐标/资源导出统一用米，具体比例经 A/T 样件复核。
- 目标阵列的试验物料：结构件 4、线缆 2、光伏片 6。光伏片随 fixture 提供且不设新配方；不要因为首个闭环缺不可制造部件而发明配方。
- 初始仓内有 1 个未预留结构件、4 铁矿、6 光伏片；无铁料、铜料或线缆。试验配方：2 铁矿→1 铁料，2 铁料→1 结构件；2 铜矿→1 铜料，1 铜料→2 线缆。因此补足目标需额外采入 8 铁矿与 2 铜矿。这是可复核的物料算例，不是实机结果。
- 两件备件中一件保护不供普通扩建；维护工位和安全补能有可达路径。维修消耗、功率、机器人初始电量/耐久、任务工时由 P0 填为固定参数，未填不得跑性能或宣称完整场景。
- 中途结构件/线缆不自动赠送。地形改造有工作、占地与设备要求，但整平不额外产矿。完成定义包含真实建成和能力增加，不只是看板勾选。

## 相机与画面对齐

以普通白昼、正常指挥距离为主；一份共同 layout，保存总览/作业/近距三台相机。建议先以 RTS 斜俯视固定方位测试；具体俯角和透视参数由同场景 A0 小样核定，不能 A 用电影镜头、T 用空场景比较。

原始坡地、整平中、建成、矿点开挖四个状态使用相同取景和界面占位。正常 UI 按输出分辨率绘制，不用降低中文面板清晰度换三维性能。

## 必跑场景变体

| ID | 变化 | 预期检查 |
|---|---|---|
| S01 | 晴天，已知路径可达，材料短缺 | 单次目标形成真实前置链并建成；不逐单要求玩家操作 |
| S02 | 改为部分材料已在途，或被其他目标预留 | 算净缺口，不重复承诺；在途到达前不算仓库可开工材料 |
| S03 | 缺加工能力且前置设施未授权 | 展示整体追加成本并待批准，不越权补建 |
| S04 | 唯一关键组件无来源/前置自举循环 | 说明具体阻塞，不无限扩任务或宣告整个基地死亡 |
| S05 | 两目标竞争设备、备件、充电和维修位 | 有界协调、保护库存、稳定任务承诺和可见等待 |
| S06 | 预报后环境增耗，相同任务/路线 | 对比固定 10% 与动态预算；记录产出/工时降低，禁止无依据再扣同一笔产量惩罚 |
| S07 | 未预报突变或预置零电故障档 | 原地停机、货物保留；不靠故意忽略已知风险制造事故 |
| S08 | 零耐久，或零电+零耐久 | 真实拖回、维修和补能，两个故障原因都要解除 |
| S09 | 救援回程电量不足/充电点停电/路线改变 | 不发起已知不安全连环救援，改计划或待条件 |
| S10 | 改地形中取消、共享前置、在途货物 | 已提交地形/成果保留，受影响区域安全，其他目标不被误删 |
| S11 | 暂停、读档、换提供者后模型结果晚到 | 无暂停推进、旧会话提交、重复扣料或产出 |
| S12 | 断网且无游戏账号，使用已安装本地组件 | 核心委托/建设/保存可完成，不能暗中调用 API |

天气数值、预报时点与实际变化时点必须分开记录；决策者只看已获得的信息。测试预置故障用于覆盖状态机，不是假装普通玩法必然会坏。

## 压力档按同一规则扩展

沿用现有技术计划的 S=12 台/6 初始设施、N=100/50、P=500/200，X 沿曲线探索极限。N/P 需有真实任务、运输、充电、维护与竞争；增加图标不是增加模拟负载。每档固定地图、资产、并发目标和故障分布，规模不是游戏最终上限承诺。

每档测试 ×1/×2/×4，模型关闭仅作成本对照；通过声明必须使用满足本地能力要求的推荐模式。不要让三条原生/超分对照分别用不同镜头、粒子或模型队列。
