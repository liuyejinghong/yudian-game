## 结论

现有产品决定足以开始有限验证，没有必须先由所有者重新选择的产品方向。尚需明确的是验证场景的执行约定，不是重新讨论画风、平台或模型名称。本包给出可执行的试验默认；这些默认不自动升级为正式平衡、最终存档协议、最低配置或商业承诺。

最初用户允许“按下一步验证；无法实测则规划两条路线”。当轮实际执行的是仓库读取、逻辑审查、环境检查、官方资料核对与文档交付，没有替用户在 Mac 上启动程序，没有购买资源、下载权重或调用付费 API。下方能力表是最初 V0 的历史检查，不表示后续会话已经重新运行。

## 开工方式

先由一个 Codex 主控完成共享约定登记（P0），再让 A 和 T 在各自工作树中并行；工程入口、依赖、共同 fixture 与集成场景只有一个写者。两条提示词分别位于 A/T 文件末尾，可直接作为任务说明。

A0 概念探索与 T0 环境核定可以同时开始；A 的三维样件接入依赖 T0 核定的导入约定。美术图可以帮助选择，但真正的联合验证必须使用可运行资源，不是截图背景。

已安装且合法可用的工具优先。新增引擎、SDK、模型权重与资源必须先记录版本、许可、体积和用途；未获下载/费用授权时报告 BLOCKED，不自动购买、调用付费 API、升级整个系统或把巨量权重提交 Git。

## 交付与授权边界

交付一个小型验证工程、可复现实验与明确技术建议，不交“完整游戏”，不称为 EA。没有证据时写 NOT_RUN/BLOCKED，允许部分完成但不签总体通过。

旧仓库、生产环境、公开/私有状态、仓库许可和历史文档不在操作范围；不强推、不合并 PR、不删档。具体依赖和模型结果通过后再形成独立 ADR 与 G1 工作包。
