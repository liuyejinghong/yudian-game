# 分层 agent 工作合同：主控、执行与独立验收

> 历史快照（2026-10-03；2026-10-05整理）：保留当时计划与证据边界，不代表当前工程状态或自动开工授权。当前任务与执行合同以[双线TODO](../../TODO.md)及其链接为准。

日期：2026-10-03｜proposal-1。状态：组织与任务规格建议，尚未进行本项目模型能力评测；不授权模型账户调用、发布或全路线实施。

配套：[原型与版本路线](05-prototype-version-roadmap.md)、[V0 总入口](README.md)。Codex 是开发执行环境/工具；这里所称“主控”是其中承担强推理、接口和集成职责的模型；GLM-5.3-Flash 是所有者提供的开发期执行模型，不因此自动成为玩家客户端的运行模型。

## 1. 基本原则

按所有者描述的相对能力，先采用“强模型做高歧义决策和首件，GLM 按已验证模板做有界扩展”。这不是官方能力排名，也不假设便宜模型只能做简单工作。后续按本项目的小任务结果调整。

几乎无限 token 不是几乎无限合格改动。主要约束可能变成主控审查、集成、GPU 试验与所有者注意力。目标是增加通过验收的产物，不是增加代码、PR 或模型讨论的数量。

主控负责把任务变得容易验证；不能只把一个模糊的大功能扔给 GLM，等出错以后再用强模型重写。

## 2. 角色和权限

| 角色 | 负责 | 不越过 |
|---|---|---|
| 所有者 | 产品方向、审美与体验、重大范围/费用/发行决定 | 不承担函数签名、并发算法、引擎参数选择 |
| 强模型主控（Codex） | 风险拆解、当前版本 spec、冻结接口与 fixture、第一份端到端实现、难点、集成 | 不用个人偏好重开已确认产品方向 |
| GLM 执行者 | 规格内代码、资源清单、局部 UI、验证脚本、按模板扩展、测试变体候选 | 不自行设计全局架构、改经济与故障规则、越文件边界或合并 |
| 独立评审 | 对照要求、检查越界、运行强模型冻结的验收和留出场景、回归 | 不只看执行者自述“已通过”；不把多数模型同意当真人可玩性 |

评审可以由相同强模型的独立会话承担，但须独立阅读输入与结果，不把实现者总结当唯一依据。重要判定由实际测试和人工体验支撑，而不是依赖模型换个角色名。

开发模型/工具与运行时模型/供应商分开。所有者开发 token 额度不能用来承诺玩家无额外费用或客户端可离线使用。

## 3. 三类任务

### 绿色：适合交给 GLM 起步

依据现役资料整理有溯源的资产/状态清单；按冻结字段生成文档或格式校验；已经有一份正确样例后的相似 UI 组件；资源命名和元数据检查；按主控定义生成故障输入候选；独立纯展示函数；有确切预期的批量转换脚本。

“补测试”并不让 GLM 自己定义正确答案。业务 oracle、关键期望与保护测试由主控/评审锁定；执行者可以新增测试或提出冲突，不能改期望来让错误实现变绿。

### 黄色：首件通过后才委托

单对象场景选择、相机边界、已冻结状态到表现的适配、简单数据加载、已验证模型资产的同类扩展、局部性能采样工具。

先由主控做一条可运行首件，明确生命周期、引用方式与错误处理，再将不共享文件的相似项交给 GLM。每项仍独立验收。

### 红色：主控持有设计和集成，不整体外包

目标规划与搜索边界、资源预留/去重、共享前置取消、能耗和安全返程、救援可行性、地形/碰撞/导航一致性、异步模型与读档失效、存档迁移、跨线程提交、Metal/超分集成和性能瓶颈诊断。

红色模块内部可以切出已充分冻结的纯函数和数据任务给 GLM；“参与实现”不等于“拥有系统决策权”。不得下发“实现完整 AI 规划器”“优化所有性能”“把地形系统做完”这类开放任务。

## 4. 一项工作的闭环

1. 主控先冻结目标、输入输出、依赖版本、可写路径和验收。
2. GLM 简短复述目标与边界；发现缺口则报 BLOCKED 或提交选项，不替产品拍板。
3. 在独立 branch/worktree 中实施，只修改白名单文件。
4. 运行规定命令，保留命令、退出码、失败输出和测试环境；缺环境标 NOT_RUN。
5. 提交小型 diff、实际证据、未完成项和可能风险。
6. 独立评审核对 spec、保护测试、隐藏/留出变体与真实效果。
7. 主控按依赖顺序集成，跑跨模块回归；合并/发布仍按所有者授权。

分支隔离不能解决同一文件的设计冲突。主工程配置、共享协议、存档 schema、主场景、依赖/锁文件和共同 fixture 各有唯一写者；不同工作树不等于可以同时修改它们。

同一任务两次局部修复后仍不能达标，默认升级到主控诊断，而不是利用便宜 token 无限循环。两次是起步管理建议，可根据实际记录调整。

## 5. 并发与试运行

起步用 1 个主控＋1 个 GLM 执行会话，先跑五个范围清楚的小任务。达到可接受的一次验收率、无严重越界且主控复核成本可控后，再扩成 2 个互不写同一文件的执行会话。

记录：首轮验收通过率、返工轮次、主控审查时长、越界修改、集成后缺陷、回归是否覆盖真正要求。五个任务和并发数是建议的校准规模，不是关于模型性能的事实。

不要同时开十个 agent 生产无处集成的代码；提交队列应按主控消费能力限流。把重复的确定性工作变成脚本后，不再消耗模型反复生成同样结果。

Mac 图形/模型/性能测试同一时间只跑一个受测任务，不与多个构建或本地大模型争抢资源后还把数据当干净基准。

## 6. 工作项 spec 模板

```markdown
# WK-编号：可验收的一件事
状态：DRAFT / BLOCKED / READY / IN_PROGRESS / REVIEW / ACCEPTED
所属里程碑：
需求来源：现役文件与条目；该来源的版本/提交
问题：玩家或开发者遇到什么，而非实现者偏爱的结构
结果：本项完成后可观察的变化
非目标：明确不做的邻近功能
前置：需要先通过的接口、首件、依赖与环境
基线：精确 commit 与 spec revision
只读上下文：3–5 个必要文件及相关段落，不投喂全历史
可写文件：完整白名单；报告文件也要列入
禁止修改：共享合同/规则/测试期望/依赖等明确路径
输入输出：类型、单位、状态、异常与副作用
验收：Given/When/Then；正常、边界、取消/失败等本项相关场景
执行命令：必须已经存在，并附运行目录、依赖和成功条件
证据：命令退出码、日志/图像、构建/资源 hash、未做项
复核：主控/独立评审持有的保护测试与留出检查
升级条件：接口不足、必须越界、两轮修复仍失败等
交付：diff、实际结果、未完成与风险；不自行合并
```

READY 需要 exact baseline、可用命令和明确文件归属。仅有文件夹建议、伪代码接口或“测试自己想办法”的票据仍是 DRAFT。后续工程里的路径不得被说成现在已经存在。

一项绿色任务原则上只处理一个行为，通常控制在 1–3 个文件及可短时复核的 diff；这是审查预算，不是允许把复杂设计压缩成难读的三百行代码。超出边界先拆分。

结果：得到一份可用于制作与核对的“资产—任务—状态”对照表，而不是新增世界规则。

只读来源：`docs/art/art-direction.md`、`docs/product/energy-return-and-rescue.md`、`docs/decisions/decision-register.md`。本文件制定时的 main 基线为 `38cff8e02914ddb2d69d0c310cf3c41ca850bd2a`；执行前回查。

验证：在仓库根执行现有 `python3 tools/verify_documents.py` 和 `python3 -m unittest discover -s tools -p 'test_verify_documents.py'`，随后独立评审逐行抽查来源。前两项只验证文档工具，不证明内容语义无误。只提交新增表和真实命令结果，不下载或生成图片，不安装软件。

本任务价值是把已有设定变为制作清单；它不是让 GLM 重新做美术总监。原型未启动时即可开展，不用等待 Godot。

## 8. 工程建立后可下发的代码示例：WK-UI-001

状态：DRAFT / BLOCKED_BY_T0。拟属 v0.0.1。以下是供主控冻结的小任务示例，不宣称函数、路径或 dotnet 测试项目已存在。

结果：只读能量与耐久数据，产生正确的中文状态显示，不决定返航，不修改任何世界状态。

建议输入合同：整数 EnergyWh、CapacityWh、Durability、MaxDurability；电量与耐久各独立验证，必须在 0 到对应正上限之间。输出 BatteryText、ConditionText、FaultLabels。主控在 T0 后绑定实际类型，不让执行者另造 DTO。

建议测试期望：
- 100/1000 Wh、80/100 耐久：电量文本 `10%`，无零值故障标签；该函数不因 10% 发出回充命令。
- 电量 0、耐久 80：包含 `零电停机`，不显示维修已经完成。
- 电量 100、耐久 0：包含 `机械故障待回收`，不以充电解决耐久。
- 两者均 0：同时保留两个故障原因。
- 电量/容量字段非法：该栏显示 `状态未知`，不除零、不把负数夹成看似有效的 0%；独立有效的另一栏仍正确显示。
- 重复调用不改变输入，不创建任务、不发网络请求。

拟可写范围只包括一个展示函数文件和一个对应测试文件；具体路径、编译命令、测试命令与主控持有的 oracle 必须在 READY 前补齐。不得修改真实能耗、返程预算、状态机或保存逻辑。

这类票据适合 GLM，因为正确行为已被定义且可自动核对。相反，“设计充电和救援系统”不适合作为同级别票据。

