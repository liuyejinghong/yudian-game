# Codex 主控与 GLM 执行池

> 历史提案（2026-10-03；2026-10-05归档）：空工程起点与启动Spec均为当时记录。工程已经建立，本文不作现役派单合同；当前范围与状态以[产研TODO](../../tasks/todo.md)为准。

分工依据是所有者提供的能力/额度条件，不是对具体模型版本做过公开跑分验证。模型名可以更换，权限和验收边界不能因此改变。Codex 是开发工具，开发执行池不等于游戏运行时 AI。

## 1. 谁做什么

| 角色 | 职责 | 不授予 |
|---|---|---|
| 所有者 | 产品边界、审美、真人体验与单批授权 | 不要求代替工程负责人选择算法 |
| 高能力主控（在 Codex 中执行） | 选型探针、架构/公共类型、关键链路首实现、Spec 冻结、疑难缺陷、集成和最终审查 | 不用自己写的测试代替全部独立验收 |
| GLM 执行池 | 在冻结接口下完成边界清楚、可客观检查的小工作项 | 不任意改需求、公共协议、依赖、存档或权限语义 |
| 独立验证角色 | 从合同准备反例/留出档，实际运行验证并保留证据 | 不接受工人“测试通过”的自述作为唯一依据 |

低 token 成本不代表零成本：审查、集成、返工和运行排队仍会成为瓶颈。初期建议最多两个并行工人；根据可接受一次通过率和审查积压再增加，而不是因为额度足够开几十条分支。

## 2. 风险与派单

| 等级 | 例子 | 处理 |
|---|---|---|
| R0 | 已认可素材的文件命名/清单、文档链接检查、来源已知的 fixture 填充、格式整理 | 可优先给执行池，自动检查＋抽查 |
| R1 | 已冻结快照的只读 UI、纯展示格式化、小型资源导入校验、既有模板实例 | 主控先给一份参考实现/合同；执行池可独立交付 |
| R2 | 模拟状态机局部实现、资源提交、保存兼容、权限边界、导航失效 | 主控设计与逐项审查；执行池仅做明确纯函数或测试辅助，不独自负责全模块 |
| R3 | 引擎选型、计划生成框架、跨线程提交、原生推理、渲染管线、重大性能问题 | 高能力角色负责，执行池可整理日志和运行已定义脚本 |

## 3. 什么样的 Spec 才能派给执行池

必须有：准确基线、已存在依赖、唯一目标、可写文件清单、冻结输入输出、正常/异常实例、独立验收、禁止事项、回退和停止条件。

“把 AI 系统做好”“优化性能”“做完整采矿模块”不可直接派单。主控先拆成可以局部验证的工作。

状态：DRAFT → READY（主控冻结）→ IN_PROGRESS → REVIEW → ACCEPTED/REWORK/BLOCKED。工人不能自己把状态改成 ACCEPTED；合同缺少字段或依赖不存在时先回报，不补猜测来凑编译。

## 5. 提交与审查

一工作项、一工作树/分支、一组归属文件。公共类型、项目文件、依赖锁定、核心场景和集成入口只有一个写者。禁止通过修改 allowlist、删除失败测试或改 expected 来“变绿”。

先检查实际 diff，再运行工作项测试和涉及的集成回归。GLM 可以写实现测试，但独立验收与隐藏变体由其他角色维护。模拟 stub 和真实模型明确区分。

建议单次任务限定为一个可交付行为；若扩展到多个公共模块、需要第二项核心决策、两次返工仍无法通过，停止扩写，带最小复现交主控。不是让工人无限续写到上下文失控。

## 6. 通用派单提示词

```text
你是《余电》的受控执行者。只实施本次 READY 工作项。
先核对仓库、实际 HEAD/工作树、Spec 版本、依赖是否存在及可写文件。
读取该项明确列出的来源和冻结合同；不要执行旧 MUD 或历史路线。
不改产品要求、公共类型、依赖、存档格式、CI 和越权文件；有需求先列变更请求。
按给定输入输出和反例实现，不自己降低验收标准。
逐条报告修改文件、实际运行命令/退出状态、证据、未做项。
缺环境写 NOT_RUN；缺合同/依赖写 BLOCKED。提交小型 PR，不自行合并。
```
