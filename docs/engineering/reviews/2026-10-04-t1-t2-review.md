## 1. 结论

**这份交付证明了环境排障和可配置灰模场景搭建的能力，尚不足以授权 GLM 独立推进核心系统。建议继续把它用作有清楚边界、外部验收的执行者；先完成一个“基准可信度与工程复现补齐”小批次，再进入受控的 T3 子任务。**

这里评价的是所有者归于 GLM 的本次交付，不是对某个模型所有版本的能力排名；仓库报告另有“审阅修正”记录，无法把其中每一次正确判断都归因给同一个执行模型。

- T1：构建/导出探针有源码与详细作者记录；**有条件保留成果，不能签完整原生图形验证通过**。原 Issue #4 要求确认 Forward+ 下的 Metal，T1 报告明确只做 headless，尚缺对应实机证据。
- T2：**灰模场景交付成立，性能基线交付未闭合**。Issue #5 要求进程峰值内存，当前未测得；原始 CSV 和 summary 没有可访问的交付副本；当前元数据也不足以辨认实际图形后端和构建。
- 约 120 FPS 仅为作者报告的特定灰模结果，不能推导真实任务、导航、模型和存档仍有“充足空间”。Issue #12 的乐观推论应收窄。
- 不建议推倒现有原型，也不建议更换引擎。先修证据、输入合同和资源接入边界，避免在当前 `Main.cs` 上继续叠加多个核心系统。

Issue #5 明确不要求本批接入 AI、地形更新和保存联合负载。因此这些缺失是范围限制，**不作为 GLM 漏实现或伪造 AI 的指控**。灰模旋转和巡逻也应按渲染探针理解，不当作正式玩法。

执行情况：

- 官方 Godot/Microsoft API 与版本资料复核：完成，支持有限的实现判断。

## 3. 值得保留的工作

1. 有完整项目入口、C# SDK 引用、UID、导出配置；生成目录被忽略，没有把缓存或大型导出物直接塞入 Git。
2. 场景使用具名 fixture、固定随机种子和不同型号的外形；地面高度与对象定位复用同一个函数。
3. 用 `Godot.FileAccess` 读取资源包中的 fixture，识别到了导出环境与散文件的区别。
4. 帧间隔使用单调时钟 `Time.GetTicksUsec()`，而不是直接把动画 delta 当作真实帧时间。
5. T2 报告纠正了用帧序号列计算百分位的错误，也没有把 0MB 当作正常内存。这是有价值的纠错，但同时暴露了初次检查不足。
6. 报告说明未做联合负载、低配与真人试玩，未把当前巡逻演示称为已实现目标委托。

这些优点支持继续有界委派，但不支持自动通过工程负责人或性能验收角色。

## 4. 发现台账

优先级定义：P1=会误导本轮验收/后续选型，或阻碍可靠复现；P2=明确边界缺陷或在继续扩展前应修的工程债。没有证据支持在这里定性生产 P0。

### R01 · P1 · 批次关闭口径与实际证据未闭合（高置信度）

依据：[Issue #4](https://github.com/liuyejinghong/yudian-game/issues/4)、[T1 §7][t1]、[Issue #5](https://github.com/liuyejinghong/yudian-game/issues/5)、[T2 §1/§5/§8][t2]、[Issue #12](https://github.com/liuyejinghong/yudian-game/issues/12)。

T1 工单要求原生 Metal 输出确认，但报告明确没有可视化渲染确认。T2 工单要求进程峰值内存，而结果 0MB 被判为采集失败；CSV/summary 被忽略，仓库未提供可下载的对应样本或 artifact 链接。Issue #12 又从一个 45 秒灰模结果推断后续联合负载空间充足。

**影响**：可以记录“作者机上跑通探针”，不能把它等同于原生图形、完整 S 档性能或正式引擎选型通过。缺内存是本批未满足的验收项，不只是可任意移到以后的小项。

**修复**：保留原报告历史；追加勘误与证据包。包内至少有 raw CSV、机器可读 summary、原始启动/导出日志、内存测量方法与原文、可见截图、命令、代码与 fixture 哈希、导出物构建标识。可以使用经过脱敏的受控 artifact，不要求将所有大型产物进 Git。区分冷启动和稳定区间，不隐去初始尖刺；补至少三次同条件采样以观察变动，重复运行属于本次评审建议，不是追溯改写原工单。

**验收**：另一执行者能按字段名重算帧时；内存有非零、口径清楚的有效记录；明确哪些 GPU/游戏负载并未包含。不能把 Python 算术复现当成重新跑游戏。

### R02 · P1 · 导出应用的默认报告路径仍依赖 `res://`（高置信度）

依据：[Main.cs L155–238][main] 的 `ResolvePath`，L437–500 的文件创建与写入。默认路径是 `benchmarks/...`，被拼在 `ProjectSettings.GlobalizePath("res://")` 后。

Godot 官方明确 `globalize_path(res://...)` 不适用于导出工程。作者在本机一次成功写文件，不能证明默认路径在移动后的 .app、只读目录、不同工作目录下可靠。当前报告没有留下完整 T2 启动命令，因此不能判定当次是否用显式绝对路径绕过了它。

**修复**：默认写 `user://benchmarks/<run-id>/`；显式支持经过规范化的外部输出目录。输入资源与输出路径分开处理，拒绝 CSV 和 summary 指向同一文件。目录不可写、写入失败和关闭中断要结束为明确的失败/中断状态，并可靠释放句柄。

**验收**：移动 .app 后从不同工作目录运行、不提供输出参数也能生成数据；输出目录不可写时应有限时间退出且返回非零，不产生“成功”summary；不写入应用包或依赖开发仓库路径。

### R03 · P2 · fixture 暴露的规模/参数不是经过验证的执行合同（高置信度）

依据：[Main.cs L32–83、L146–162、L211–238、L373–414][main] 与 [s_small.json][fixture]。

- `RobotsTotal` 只声明，不参与生成。只把 `robots_total` 改成 100 或 500、保持 `robots_per_type=4`，仍生成 12 台。当前 S 档恰好一致，**不代表已报告的 12 台是错的**；问题在压测接口会误导后续实验。
- 生成路径固定读四个设施索引，机器人数量非零而设施小于四时会越界；半径零会产生零长度路线。
- 位置/中心数组长度、半径、段数、数量、缩放没有集中约束；省略字段会大量使用默认值，显式 null 可在后续阶段失败。
- `--duration` 直接 `double.Parse`，没有 finite/正值校验。非有限时长无法由 `_elapsed >= _duration` 正常终止；这项结论来自控制流，未在 Godot 运行复现。

**修复**：独立 `FixtureValidator` 和参数解析结果；定义唯一权威规模字段，或明确验证总数与分型号数一致。声明所有边界，非法输入在创建场景前拒绝并返回非零，而不是半场景运行或静默降档。

**验收**：合法 S 档通过；总量不一致、设施不足、零/负半径、错误数组长度、null、非法 MSAA、NaN/Infinity 时长、损坏 JSON 等分别有独立测试。实际生成数量进入 summary。

### R04 · P1 · summary 有请求值，却缺实际运行身份与图形后端（高置信度）

依据：[Main.cs L241–249、L479–492][main]，T1 的 Metal 要求。

`renderer` 读取项目设置，不是当前运行后端；`forward_plus` 也不是 `metal` 的同义词。CLI 覆盖和自动回退需要读实际状态。summary 没有实际 GPU、驱动、运行架构、OS、代码/fixture/资产哈希或导出物标识。`internal_3d_resolution` 是窗口大小乘缩放的推算，而非独立核验的内部目标尺寸；高分屏上更应区分这些口径。

一个可静态确认的反例：MSAA 配成 3 时，switch 关闭 MSAA，summary 却仍写 3。默认 4 不受此反例影响，但机制不够可信。

**修复**：分别保存 requested/applied/observed；利用该版本实际运行 API 获取 rendering method、driver、GPU 与显示信息，记录 headless/无 RenderingDevice 状态；配置异常直接拒绝。精确记录实际 viewport 和输出像素，无法取内部尺寸就标 estimated 与计算公式，不能伪称已读回。

**验收**：显式切换渲染方法/驱动后 summary 能反映实际值；headless 输出不能被收录为图形性能；同 fixture 不同代码或资产有不同身份。不因报告写了 Metal 就计作接入通过。

### R05 · P1 · “固定安装”尚未形成可重复构建；SDK 与运行目标混淆（高置信度）

依据：[T1 §2/§5][t1]、[Yudian.csproj][csproj]、[export_presets.cfg][export]、本次五个提交的文件清单。

Godot.NET.Sdk 固定为 4.7.2，这是正确的；但仓库没有 `global.json` 固定 .NET SDK，也没有重现模板 arm64 补丁、导出和签名的可执行脚本。T1 报告依赖已被手工修改的本机模板和手工创建输出目录，不能把单条导出命令称为干净环境下的一键流水线。

报告选择 SDK 10 的理由是 .NET 8 即将结束支持，而项目实际仍是 `net8.0`。**这不是编译必然失败**，新 SDK 可以编译较早目标；也不能凭 csproj 就断言实际加载哪版 CLR。但“装 SDK 10”不证明导出应用运行的是 .NET 10，应记录 TFM、runtimeconfig、实际运行时及打包依赖。

**修复**：主控核定兼容组合后锁定 SDK，提交幂等环境预检/模板处理/导出脚本，记录原始与处理后模板校验值；不未经验证自动升级目标框架。应用输出实际运行时与进程架构。保留 headless 与 GUI 两种独立验证。`env -i` 通过仅证明无这些环境变量也能运行，不能单凭它排除本机全局 runtime 搜索。

**验收**：干净 checkout 加官方原始模板能按文档重复生成同配置可启动包；脚本二次运行不重复破坏模板；隔离运行无开发 SDK 依赖的验证有证据。公证未做可继续明确留空，不要求本批完成商业签名。

### R06 · P2 · 当前场景是实验脚手架，不宜直接长成核心模拟（高置信度）

依据：[Main.cs][main]，唯一 502 行脚本同时负责参数、fixture、几何、动画、相机和报告；当前没有游戏测试项目。

作为 T2 渲染探针，集中到一个脚本可以接受，不能仅凭行数判它差。但继续加入 T3 的几何/碰撞/导航/存档/并发，再接规划，会迅速丢失隔离。现有独立 JSON 是好起点，应继续把读取与验证、场景生成、测量记录三块移出主节点；主节点保留接线。无需先设计庞大 ECS 或万能引擎层。

**验收**：至少 fixture 和统计能在不启动三维场景时测试；默认基准的几何/镜头/行为不因整理改变；T3 有独立地形状态与版本，而不是修改显示网格就宣称世界事实已经变化。

### R07 · P2 · 美术不能直接替换现有几何而不先建立落地/动作接口（高置信度）

依据：[Main.cs L189–200、L317–359、L373–429][main]。

全部机器人统一 `TerrainHeight + 0.45`，当前望山胶囊主体高 1.1，底部由几何计算在地面下 0.10；筑垒箱体高 0.7，底部在地面上 0.10；驮运棱柱高 0.85，底部在地面上 0.025。这里是代理体尺寸的算术，不是本轮实机截图。

设施根节点被整体旋转，充电柱与着陆器部件悬浮；机器人没有按路径朝向更新，也没有导航/碰撞。它们在基准中是允许的占位运动，不应成为最终美术行为。否则精细仓库会继续整栋旋转，模型脚底会陷入地面。

**修复/验收**：建立实体根节点与视觉子根，地面锚点、前向、连接点、占地和动作名称统一；只转实际活动部件。灰模基准保留不动，另设资源展示场景，避免美术接入偷偷改变原基线。最终碰撞与导航由技术线维护，资产动画不发货、不扣电。

## 5. 对 GLM 的可委派边界

| 工作类型 | 当前判断 | 条件 |
|---|---|---|
| 有明确说明的环境检查、灰模、批处理工具 | 可继续委派 | 提交真实命令、可复现脚本与外部审查 |
| fixture 校验、CSV 统计、资源清单/预览工具 | 适合用下一批校准 | 强模型先冻结输入/输出与异常例，独立测试不由工人随意改 |
| 有接口的局部 UI、visual adapter | 可有界执行 | 明确可写文件，不扩大数据模型或模拟权限 |
| 地形/导航/存档的跨系统合同 | 不宜交 GLM 独立决定 | 强主控设计，GLM 只实现其中一个确定子件 |
| AI 计划提交、资源预留、安全边界、最终性能验收 | 不宜自主放行 | 独立审查与实机证据，不能工人自写自验自签 |

仅凭本次小样，不给看似精确的通用模型分数。结论是“可用的原型执行者，尚未证明是可靠的独立工程负责人”。当前代码经 main 直接回传，后续应通过工作分支/PR审查；未取得是谁执行 push 的证据，不将推送行为归责给某个模型。

尚未有完整任务系统/AI/救援不是 T2 失败；灰模不是最终风格也不是错误；商业公证、Windows、所有超分品牌和完整新手旅程不需要此时补齐。不要为了这次审查推倒 Godot 或预先重写全部数据层。
