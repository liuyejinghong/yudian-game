# 技术选型与性能验证计划

版本：v0.1 基线＋v0.4 专项入口｜2026-10-03  
状态：**官方资料调研已做；项目实机验证 NOT_RUN；尚未最终冻结引擎、渲染器、地形或模型版本。**

最新补充：[超分辨率与平台加速](upscaling-and-renderer-evaluation.md) 纳入选型验证；[返航与救援](../product/energy-return-and-rescue.md) 的天气增耗、停机、拖运和修复加入相同负载。超分／插帧不能替代模拟与规划优化。

## 1. 选型的依据和责任

依据产品要求：macOS Apple Silicon 原生首发、Windows 后续、本地单人存档、RTS 斜俯视实时 3D、目标委托与本地 AI、真实地表改造、机器人电力／耐久／维修、非高配门槛。

所有者不需要替开发者选择算法。技术负责人应提交可复现结果、明确推荐、风险与失败出口；不是列几个引擎名字让所有者凭感觉投票。Codex 执行验证，所有者决定画面与产品取舍。

当前首选验证路线仍是 **Godot 4 .NET＋C#**。它是领先候选，不是不可质疑的已验证结论；当前新仓库没有可运行工程，不应因为文档写了名字就批量制作依赖它的内容。

如果候选在目标负载、原生依赖或所需功能上出现无法合理局部解决的问题，才启动 Unity＋URP 的相同负载对照；不在产品前提不变时无止境泛泛比较引擎。更换之前给出最小复现、剖析结果、尝试过的优化和迁移代价。

## 2. 官方调研能支持什么，不能支持什么

以下沿用 v0.3 文档包的 2026-10-03 官方材料记录。相关链接可能持续更新，因此最终冻结应记录所用具体版本；本次新核对的 MetalFX／FSR／DLSS／XeSS 资料见专项文档，不能把历史查阅全部说成本轮重新验证。

| 事实 | 来源 | 对本项目的有限结论 |
|---|---|---|
| Godot 的 .NET 桌面导出包含 macOS／Windows；C# 与引擎交互有互操作开销 | [T1] | 可以进入候选；热循环不反复跨场景 API；不能据此声称项目原生性能已通过 |
| macOS 导出涉及应用包、架构、签名与公证 | [T2] | 需要真实打包与分发验证，而非只有编辑器能运行 |
| Forward+、Mobile 可用 Metal；Compatibility 使用 OpenGL，功能不同 | [T3] | 同场景比较前两者；不能按“Mobile”名称断言一定更快 |
| LOD、可见性范围、实例化、透明物与灯光成本属于实际优化面 | [T4] | 资源规范和场景密度要进入测试，不能只测试纯几何空场景 |
| 导航性能包括几何提取、烘焙、路径查询与同步成本 | [T5] | 地形修改需要测局部导航更新，不能每次全图重烘焙或全机群同帧重寻路 |
| CPU 优化需用 profiler 定位，C# 的 GC、节点数量与互操作需要关注 | [T6] | 保持模拟数据与视图分离，按证据优化而非口头选择“最快语言” |
| llama.cpp 支持本地推理与 Apple Silicon／Metal 等后端 | [T7] | 可以验证本地文本／部分模型；不证明它支持所有分类器，或 1–2GB 已足够 |
| Codex 可按 AGENTS.md 读取项目指引 | [T8] | 当前需求必须有单一入口，历史文档不能冒充现役指令 |
| Unity URP 有专门的性能分析指导 | [T9] | 存在对照路线，不提供跨引擎性能优劣结论 |

**文档确认能力存在，不等于《余电》完成接入、调优或低配验收。**

## 3. 候选架构：可替换热点，不做可替换一切的框架

建议的职责：

- **模拟核心**：C# 数据与规则；维护资源、地形状态、任务、机器人健康和世界时间。尽量不依赖场景节点，支持无画面的规则测试。
- **目标与计划**：领域前置图／层级任务或其他候选规划方法；分类器／大模型提出或选择合法方案。模型未验证之前，不把特定提供者写进存档身份。
- **提交与校验**：检查权限、资源、计划版本、地形可达性、对象健康；只提交有效变化。已接受模型决定可记录用于回放，读取时不重新收费生成已完成决定。
- **表现**：Godot 场景与原生 UI，只投影真实状态；动画不产矿，渲染帧不扣耐久。
- **本地模型适配**：共享模型实例／有界队列；候选原生库或受控辅助进程；取消、超时、迟到拒绝和离线能力可测试。
- **存档**：版本化世界快照与必要历史，地形差量有边界；安全替换、备份与迁移。无需给玩家安装 Fastify／PostgreSQL。
- **平台适配**：路径、输入、平台功能、推理后端与打包隔离，避免 Mac 专用实现散落全项目。

先划清这几条边界，不先做通用工作流平台、万能事件溯源平台或庞大 ECS。并行计算只读稳定快照，在提交点重验；不在模型请求期间锁住整个模拟。

## 4. 地形方案必须在选型验证中处理

产品要求是有限地表削平、清场与矿点开挖并持久化。技术可以比较：受控地块的阶段网格／形变、局部高度场修改，或足以满足要求的其他轻量实现。

比较维度：

1. 视觉能否明确看出坡地变平、矿点被挖开；不只换贴花。
2. 几何／碰撞／导航／施工合法性是否同源；取消与重载后是否保持一致。
3. 改造中更新范围、主线程峰值、导航重算和内存增长。
4. 存档大小是否随操作数无限增长；阶段合并／差量压缩是否影响真实历史。
5. 多机器人和两个相邻工程同时作业时，有无过期提交、路径震荡或重复收益。

首期不采用任意体素世界作为默认，更不以“不做体素”为理由砍掉真实地形改造。全局高精度土壤物理、多层洞穴和土方物流尚未获确认。

建议使用简化碰撞／导航代理、分区版本与受影响任务重评；路径缓存随区域版本失效。具体实现通过探针决定，不直接锁死某插件。

## 5. 参考硬件与低配置责任

已知开发设备：14 英寸 MacBook Pro，M3 Pro 满血配置，36GB 统一内存。它是开发与高档参考机，不是最低配置。

以下是**待获取设备和待确认的试验目标**，不是商店配置或本轮成绩：

| 档位 | 候选设备／条件 | 初始目标（提议） |
|---|---|---|
| D 开发参考 | 所有者 M3 Pro／36GB；记录系统、供电、温度、分辨率 | 1920×1200 中档场景，目标 60fps；正常模拟与本地 AI 同开 |
| L 低配探针 | 原生 M1／8GB 或其他明确较低配置实机；不可由开发机内存限额模拟替代 | 1920×1080 低档目标 30fps；仍有完整本地目标委托、地形与健康规则 |
| M 中档探针 | 较早 Apple Silicon／16GB 级实机 | 观察本地模型、资源流送与后期规模是否有合理余量 |
| W 后续 Windows | 支持时再固定 CPU／GPU／RAM 与驱动 | 共享规则和资产；单独图形、原生推理、存档和发布回归 |

暂时没有较低配置设备时写 **L/M NOT_RUN，最低配置未确认**。禁止仅凭 36GB 机器通过就宣传低配置友好；也禁止强制低配玩家改用付费 API 来掩盖本地能力失败。

## 6. 可复现的负载档

规模为验证建议，在执行前锁成具名 fixture，不是承诺游戏最终支持数值。

| 档 | 候选规模 | 必须运行的真实逻辑 |
|---|---|---|
| S 小切片 | 12 机器人、6 设施、少量并行目标 | 缺料补齐、整平、开挖、回充／维修、保存重载 |
| N 日常扩张 | 100 机器人、50 设施、多个竞争目标 | 调度、运输、健康变化、局部导航更新、本地推理 |
| P 后期压力 | 500 机器人、200 设施、较密任务与已开发地块 | 长程累计、集中重规划、充电维修争用、存档体量 |
| X 寻找极限 | 按曲线继续扩展，不提前许诺上限 | 找到 CPU／GPU／模型内存／寻路拐点，不只生成移动图标 |

每档锁定地图、镜头位置、资产版本、任务初值、随机种子、模型／量化／上下文、并发和画质。分别测模型关闭对照、推荐本地模型开启，以及允许的倍速。固定 seed 不保证大模型重复调用一致，所以记录实际已接受结果。

## 7. 联合测试，不是独立跑分相加

重点工况：三维画面＋目标前置展开＋机群调度＋回充维修＋土坡整平／矿点开挖＋导航重评＋本地文本＋自动保存。v0.4 增加天气增耗、返航改道、零电停机、零耐久拖运与恢复，不能只测试理想安全档。

至少记录：

| 指标 | 必须给出的口径 |
|---|---|
| 画面 | 帧时间 p50／p95／p99、最大卡顿、温度稳定后的变化；输出分辨率、内部三维分辨率、超分／插帧模式分开 |
| 模拟 | 请求倍速和实际推进比；单步／调度耗时；不可静默拖慢模拟来保持 FPS |
| 规划 | 目标登记反馈、首份可执行计划、首台机器人行动的延迟；成功与被拦错误分别统计 |
| 导航／地形 | 更新区域、几何／碰撞／导航一致性、主线程峰值、批量变化与取消恢复 |
| 内存 | 进程与辅助进程、CPU/GPU 共享分配、模型缓存与系统内存压力；避免共享内存重复相加 |
| 保存 | 快照捕获停顿、写入耗时、大小曲线、恢复一致性、意外退出与损坏回退 |
| 长时间运行 | 固定时间与负载内的内存斜率、任务队列积压、错误／超时率与温降效应 |

不要用模型权重文件大小当运行内存，不用平均 FPS 掩盖冻结，不用模拟提供者成绩标成真实模型通过。候选 p95／p99 与延迟预算由第一次基线复核后冻结，先给原始结果。

## 8. 优化顺序建议

先检查明显重复计算与结构问题：不每帧重规划，不让每台机器人扫描全基地，不重复生成已有在途产出，按事件或相关版本更新；简单代理与分组寻路避免集中峰值。

然后根据测量调整资源：共享材质／几何、LOD、局部范围、低成本阴影和适当动画更新；保留真实地形和服务状态。实时放置建筑与可变地形不应依赖一张不可改变的全图静态光照来获得唯一正确表现。

模型与渲染共同使用设备资源，测试 CPU/GPU offload、队列和输出长度；共享权重、独立机器人状态。对关键非生成决策应有低成本方案，不要求机群每 tick 调用语言模型。

在证实热点后，才考虑数据布局、批处理、后台只读计算或局部原生模块；不能为了未来可能的问题先把所有代码写成难维护的底层系统。

## 9. 技术冻结的硬条件

T01 原生构建和必要依赖链可核验；T02 游戏内美术小样可接受；T03 受控地形的几何／碰撞／导航／存档一致；T04 真实目标链、能源耐久保障及停机救援可靠；T05 本地 AI 能完成核心体验；T06 参考与较低配置结果完整；T07 加载、保存、长期运行没有已知阻断；T08 许可与再分发风险有台账；T09 按超分专项完成原生与可用重建路径的同条件画质／性能／回退测试，不以集齐品牌或插帧 FPS 代替基础性能。

未全过不能说“长期技术栈已验证无风险”。某些门槛需降低时，必须说明改变了什么产品承诺，由所有者决定，不靠换成不真实的动画、删规则或强制 API 过关。

最终 ADR 应给出一个主推荐及其证据，而不是永久保留多个默认引擎。失败仍留完整记录；后期可因明确新证据调整，但不由 agent 个人偏好变更。
