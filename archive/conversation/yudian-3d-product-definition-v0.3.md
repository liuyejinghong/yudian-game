状态：**已确认产品要求＋明确标识的设计建议。Q01–Q04、Codex、两款主要美术参考、持久地表变化、机器人电力／耐久／维修及经营失败风险已获确认。引擎、算法、具体美术生产参数与最低配置待验证。本次授权为独立仓库和文档整理，不是全量游戏实施、付费调用或发售授权。**

## 1. 产品一句话

**《余电》是一款以目标委托、具身机器人协作、持续改造地表和基地成长为核心，并以电力、耐久与维修形成生存约束的单人 3D 火星基地经营游戏。**

玩家扮演远程指挥员，决定建设什么、在哪里建设、哪些事情优先，以及允许机器人动用哪些资源。机器人评估目标、补齐前置工作、组织分工，在世界中实际完成采集、运输、加工和建设。

产品承诺不是“替玩家点击若干表单”，也不是“让机器人说出聪明的台词”，而是：**目标能够变成可靠、可见、可干预的行动。**

对外表达候选：

> 你决定基地的未来，机器人负责把计划落在火星上。

此句为产品文案草案，不是已经批准的宣传语。

## 3. 玩家价值与游戏乐趣

### 3.1 玩家购买和打开游戏是为了什么

建议服务的主要玩家是：喜欢建设、系统运转和经营取舍，希望指挥能办事的机器人，而不希望重复安排同一条生产链的人。

每次游玩应带来三种感受：

**掌控感**：我决定目标与边界，能理解结果，也能改变主意。  
**委托感**：工程队会把我没有逐条交代的前置工作做好。  
**成长感**：荒地、设施和机器人活动共同记录我建立基地的过程，包括推平的坡地、露出的矿层与长期留下的开发痕迹。
**维持与恢复的成就感（本轮明确的约束方向）**：工程队能在有限电力和耐久下运转；适时维护和保留物资让基地渡过压力。如何平衡压力强度仍需试玩。

### 3.2 自动化以后，玩家还玩什么

玩家仍决定建设方向、位置、发展顺序、物资分配、风险与保护条件。机器人减少重复执行劳动，但不替玩家决定终极目标。

例如，同一批材料可以用于提高当前产能，也可以用于储备与恢复；多个目标争用同一支工程队；快速完成项目可能需要打断另一项工作。玩家给出取舍，机器人组织实施。

不得通过故意让 AI 愚蠢、随机违约或频繁出错制造“玩家有事做”。挑战主要来自有限资源、物理距离、能源、设备能力、信息不足及相互竞争的目标。

**智能不是无成本完成任何愿望。它改善组织能力，不取消世界约束。**

## 4. 核心循环

想建设或改善一件事 → 下达目标与边界 → 形成可执行计划 → 机器人协作行动 → 遇到变化时调整或请求决策 → 完成并验收 → 基地外观和能力改变 → 玩家形成下一个目标。

这是目标委托式经营，不是全基地无限托管。AI 可以提出后续建议，但不得自行接受新目标、无限扩建或改写玩家的发展方向。

第一层收益来自基地自身的成长。外部订单、货币与通讯以后可以扩展意义，不是第一轮目标闭环的必要前置。

## 5. 代表性场景：缺料也能建设太阳能阵列

### 5.1 演示前提

以下是首个代表性测试场景，不是最终新档数值：已有基本能源、可用机器人、仓储和材料加工能力；已知且可达的铁／铜来源存在；阵列所需不可自产的关键部件已具备。结构件和线缆不足，但能通过已解锁的工艺获得。

基础设施在正式新档中仍应由玩家建立；测试存档可以预置阶段状态，以避免每次验收重复前置。若加工等前置也缺失，则按 5.5 的规则展开，不暗中补建。

### 5.2 玩家输入

玩家在场景中指定一个合法位置，选择建设太阳能阵列，使用当前默认工程权限下达目标。也可以用简短中文表达同一目标，经目标卡核对后提交。

目标卡需要区分：

- **要达到的结果**：指定位置建成、安装完成并具备并网能力的一座阵列。
- **可以动用的范围**：可用物资、允许参与的工程队、允许补齐的前置和可建设区域。
- **必须保护的条件**：被其他项目占用的物资、明确锁定的设备、最低保留量等。

夜间建成不等于立即发电；“已建成／可投运”与“当前实际出力”应分别显示。验收发电效果的测试场景使用适当日照条件。

### 5.3 系统回应

不是只显示“结构件不足，无法建设”，而是建立目标，并说明：

> 阵列工程已登记。现有建材不足，工程队将先补齐结构件与线缆，再运输到现场施工。当前方案不会动用你保护的物资。

如果相关前提未验证，应显示“正在核对可行路径”，不提前承诺一定完成。

看板可展开为：

```text
目标：在选定区域建设太阳能阵列
  补齐结构件
    获得所需铁矿 → 运回 → 加工铁料 → 制造结构件
  补齐线缆
    获得所需铜矿 → 运回 → 加工铜料 → 制造线缆
  将建材运至施工地点
  安装阵列并连接系统
  检查建设结果与运行能力
```

这是依赖关系的展示示意，不是强制所有工作串行。具备资源和设备时可以并行。已有材料或在途产出应计入计划，不能重复生产。

### 5.4 世界中实际发生什么

勘测机器人识别尚未确认但获准调查的来源；工程机器人清场、整平、采集和施工；运输机器人搬运实际货物；加工设施真实消耗投入并产生材料。任务会明确绑定执行对象和当前阶段。整平／开挖只在工作实际完成到对应阶段时改变场地，不在目标提交时瞬间抹掉土坡。

玩家能从目标卡定位现场，也能从现场对象返回所属目标。计划完成后，建成设施、消耗的物资、机器人状态和事件记录一致，并可保存恢复。

**只有下单、只有任务树、只有对白或只有动画，都不算本场景完成。**

### 5.5 不同缺口的产品规则

| 发现的问题 | 应有行为 | 不允许的行为 |
|---|---|---|
| 库存不足，但原料、设备与配方可用 | 在预算内创建采集／加工／制造前置并执行 | 一律退回“材料不足” |
| 已有相关在途材料或其他项目可共享的生产前置 | 核对归属和交付承诺后复用或调整计划 | 同一份产出重复承诺给两个项目 |
| 缺一项前置设施 | 生成补建方案；在已授权设施与预算内执行，否则一次性请求扩展授权 | 悄悄造出整条新工业链，或隐藏额外占地和消耗 |
| 拟建地块需要清场或整平 | 把改造范围、预计作业和消耗列入计划；范围内执行，超界再授权 | 瞬间移除真实障碍或改变未授权区域 |
| 机器人需要补能或维修 | 将充电、补给备件、维修排班并入目标保障，核对通路和能力 | 凭空回满电／耐久，或把所有照料重新交给玩家逐台点击 |
| 矿点尚未确认 | 在获准区域创建勘探任务，得到结果后再规划 | 读取玩家未发现的矿点内容并当成已知情报 |
| 关键部件不可自产且暂无取得途径 | 保留目标并标明具体不可达原因及可选下一步 | 编造新配方、无中生有或永远显示“准备中” |
| 完全没有可行路线／形成前置循环 | 有界尝试后明确停在“需要条件”，给出瓶颈 | 无限递归扩展 TODO |
| 位置非法或目标超出已支持类型 | 解释目标为何不被受理，可保留草稿供修改 | 将无效目标伪装成正在执行 |

**“可以登记目标”“找到可行计划”“获得执行授权”“可以立即开工”“最终已经完成”是五个不同承诺。**

## 6. 下命令的产品设计

### 6.1 已确认：鼠标目标入口是可靠主入口，有限中文指令是等价便捷入口

初期支持有限且明确的目标类型：建设某个已解锁设施、为目标准备一批物资。持续维持库存或复杂综合经营目标可后续扩展；不承诺任意自然语言都会执行。

选择建筑和位置后，即使当前缺料，也可以提交“建设目标”。这与传统立即开工按钮应在名称和反馈上区分。

中文输入先转为玩家可读的目标卡。目标对象、位置、优先级、禁止事项有歧义时，要在开工前明确，而不是执行后解释自己“理解错了”。

不强迫玩家写提示词。高级设置可以查看 AI 运行方式，但日常指挥不要求知道模型参数、上下文窗口或工具调用术语。

### 6.2 成功后的后续操作

完成目标后，展示真实改善和两类信息：已经变化的能力、仍存在的限制。可以给出少量后续建议，但由玩家决定是否建立新目标。

重复任务能形成可复用的工程偏好或权限设置；不自动把一次委托升级成“永久替我发展整座基地”。

## 7. 任务看板：执行事实的入口，不是另一张工作后台

### 7.1 建议的三层结构

第一层显示玩家目标与结果；第二层按需展开关键前置和依赖；第三层查看正在执行的机器人／设备及其状态。

默认不把数十条微动作平铺出来，不要求拖拽每个 TODO 才能运行。看板与场景互相定位，完整历史收纳在详情中。

### 7.2 每个目标必须能回答的问题

| 字段 | 玩家需要知道什么 |
|---|---|
| 目标与完成条件 | 我要的结果到底是什么？ |
| 状态 | 现在在规划、执行、等待条件、等待我决定，还是已经完成？ |
| 当前工作 | 谁正在做哪件事？ |
| 依赖与阻塞 | 为什么后续工作还没开始？ |
| 投入 | 已消耗什么、占用了什么、还预计需要什么？ |
| 时间提示 | 是否能给可信估计；不能时缺少哪个条件？ |
| 变更 | 相比上个方案改了什么，为什么改？ |
| 操作 | 暂停、取消、调整优先级、改保护条件、定位现场 |

### 7.3 状态语义

“等待前置”不等于失败；“等待授权”不等于系统卡死；“重新规划”不等于重新执行已完成工作。

重规划保留目标身份与真实历史，更新尚未执行的工作及其版本。不得每次变化就把旧任务全部删掉重建。

估计时间有前提：源头未知、设备未授权或模型尚未完成判断时，应说明不确定原因，不用假倒计时制造确定性。

## 8. 机器人：有身体约束、有任务承诺，也能协作

建议继续使用望山、筑垒、驮运作为可识别的型号／分工资产；数量和最终视觉设计不在本稿冻结。

每台机器人有稳定身份、位置、电量、耐久／健康状态、能力、正在履行的任务与少量真实经历。共享决策模型不共享这些个人状态，也不需要每台机器人常驻一份大模型。

任务评估需要考虑：自己是否具备能力、是否可达、当前承诺、电量与充电需求、所需设备与物资是否可用。多个机器人可以提出承接或协作意愿，但任务与资源只能被可靠分配一次。

“自主”不等于同时对同一目标各自完整规划一遍。玩家看到的是协作的结果，而不是重复计算与互相争抢的模型群。

正常低电和维护可在授权内自动处理，但必须消耗真实能源、时间和所需材料。涉及更换被锁定设备、打断受保护项目或突破预算时请求玩家决定。

机器人表达可以有型号与性格差异，但不得凭空编造履历，或为了“个性”违反硬性保护条件。界面展示简短行动理由与约束，不需要展示模型内部推理过程。

### 8.1 电量、耐久与保障任务（C16 已确认；以下细则为设计建议）

电量是本次出工可用的能量，耐久反映损耗与健康；回充不会修复磨损，维修不会自动补满电池。具体单位、损耗曲线、维修恢复上限与是否存在不可修复报废，在数值设计与测试中核定。

建议出工前检查任务消耗、返回可达充电点所需电量、安全余量和预计耐久。保障任务与建设目标有同等真实语义：排队充电、取得备件、维修、换班或现场救援。不能每帧让模型猜电量，也不能用模型推理耗时扣除机器人电量。

低电、磨损预警、停机、被困与不可修复不是同一种状态。默认建议：零电先停机，低耐久降低可用能力或停工待修；是否永久损毁未获确认，不把一次低电自动判成“死亡”。

建议的可见信息：为什么提前回充，维修要用什么，哪些项目因此延迟，是否在动用保护资源。日常保障在权限内自动进行；系统发现继续安排会危及最低维持能力时说明后果并请求取舍，不私自动用保留资源。

完整说明见 [地表改造与机群保障](world-and-fleet-systems.md)。

## 9. 授权边界：自动做事，但不擅自做主

### 9.1 已确认：工程托管与越界再授权

玩家确认目标后，系统自动完成该工程及已批准的前置链；默认使用未受保护的现有资源与队伍。计划中新增永久设施、区域扩展和资源上限要事先可见。

在以下边界内，日常微调整不逐次弹窗：改用同能力的可用机器人、调整不受保护工序顺序、补齐已获准的建材、合法充电与维护。

以下变化需要新授权：增加未批准的永久建筑、改变建设地点或工程数量、拆除既有设施、动用保护库存、打断保护任务、跨越区域边界、超过资源预算、产生未获准的真实 API 费用。

初次整体计划审批可以覆盖完整前置链，避免每补一个工序都再次询问。后续只对超出已批准范围的变化询问。

### 9.2 玩家保留的权力

玩家能修改目标优先级、保护设备或库存、暂停目标、取消尚未实施的部分，也可以临时直接调度某台机器人。直接调度需要说明将影响哪个既有目标，并在安全交接点改变承诺。

取消释放未消耗的预留与未执行任务；已经消耗的资源、已经完成的建材和在途货物按真实状态处理，不瞬间“全部退回原状”。

多个目标共享前置时，取消一个目标不得误删仍被其他目标需要的工作，也不得重复结算已产出物资。

### 9.3 可选模式，非首批必做

保守模式可以对较多方案变化先确认；扩展托管可以授予更宽的区域与预算。首批先把工程托管做可靠，不要求三个模式同时完整上线。

## 10. 遇到变化：自动调整什么，何时找玩家

在矿点、设备健康、功率、地形可达性、路线、目标顺序或玩家保护条件发生相关变化时，系统评估受影响计划。

有合法替代路径且仍在授权内，则更新尚未执行的部分，说明变化并继续；没有则保留已完成工作，明确请求新的条件或授权。

系统必须具备有界重试与稳定承诺，不能反复把同一机器人派来派去，或频繁改方案导致没有任何产出。

模型不可用属于计算能力问题，不冒充矿物不足、电力危机或机器人“死亡”。已有安全计划可继续执行；新计划显示当前能力状态，使用获准的回退或等待玩家处理。

物理暂停与推理等待分离：玩家暂停游戏时，可以允许非消耗性的分析继续，但不推进移动、生产和资源消耗，也不偷偷承接需要玩家确认的操作。

## 11. AI 能力与运行模式

### 11.1 本产品需要的是四种能力，而不只是一个模型

| 能力 | 产品结果 |
|---|---|
| 理解目标 | 将玩家操作／简短中文变为明确目标、位置和边界 |
| 形成计划 | 根据已知世界与工艺，补齐前置条件，找到可执行路径 |
| 做选择与调整 | 比较合法方案、分配能力、响应协作及相关变化 |
| 表达 | 简短说明真实进展、阻塞、变化与结果 |

单次“在有限选项中选一个”本身不是完整的多阶段计划系统；但选择器可以与前置关系、任务分解和搜索配合。已存在的目标／任务层级规划研究和实现能够依据行动定义、任务方法与目标方法构建计划，说明此类能力并不逻辑上必须依赖自由文本大模型。[S4]

本项目建议采用组合实现：**领域约束提供真实边界；本地规划与决策能力组织行动；必要时大模型理解或提出方案；模拟系统校验并执行。**

大模型可以是重要的规划参与者，不限于润色；但生成 JSON 或一张清单不代表路径可执行。关于把模型建议与外部验证结合的研究提供了可参考的方法，论文中具体领域的结果不是《余电》的测试成绩。[S5]

不在本稿预判“所有小分类器够用”或“大模型一定必要”。最终按游戏任务、目标 Mac 的延迟和资源占用决定。

### 11.2 玩家可选择的运行方式

| 模式 | 产品意图 | 必须说明的限制 |
|---|---|---|
| 本地推荐模式 | 正常玩家无需配置外部密钥即可体验核心目标委托 | 推荐模型包和能力等级必须实测；安装完成后测试断网完整闭环 |
| API 模式 | 玩家选择经过适配的服务提升或替换某些 AI 能力 | 明确数据传输、延迟、服务依赖和真实费用；不承诺任意 API 均兼容 |
| 兼容／回退模式 | 在生成能力不可用时保护存档和已建立的任务 | 能力下降必须照实标注；不可把纯规则对照称为已验证的模型自主规划 |

**已确认的商业底线：本地推荐模式应完成首个核心建设闭环，不把可靠委托留给另外付费的 API。**若本地方案不能达标，必须重新讨论产品承诺，不能悄悄把它变为强制联网游戏。

模型选择首先显示“可用、未安装、未通过能力检查、需要更多内存”等人类可读信息。高阶配置可以查看具体模型；普通玩家不应被要求自己研究量化与提示模板。

决策与文本可以用不同提供者。切换时保留目标、已接受计划和存档，不重新发放资产，不以旧模型的迟到结果覆盖新安排。

### 11.3 本地交付与 API 的边界

建议内置受管理的推理能力，模型包可随游戏或明确下载的内容包提供；不强迫玩家另装 Python、Ollama 或远程数据库。具体捆绑方式需核对权重许可、包体和 Steam 分发方式。

llama.cpp 是本地运行候选，官方说明支持 Apple Silicon／Metal 和多种其他硬件后端；这不是本项目已经完成的集成或性能证明。[S6]

本地模式默认不传出玩家指令与存档内容。API 模式须明确哪些指令及最小世界上下文会被发送；密钥不进入存档、导出日志、截图或云同步包。真实钱与游戏内资源预算分开。

开发期可以验证用户自有 API 配置。Steam 商业版是否采用自有密钥、开发者代付或其他访问方式，属于独立待核定项：Valve 当前文档对外部实时 AI 服务的访问与付费有明确要求，不能预先把某种收费方案视为已批准。[S8]

## 12. 界面、镜头与美术

### 12.1 已确定与未确定

已确定：实时 3D、斜俯视指挥视角；美术主参考为《Surviving Mars: Relaunched》和《Anno 2205》，而非上一稿默认推荐的厚重工程 B 风格。未确定：原创造型、最终材质集、相机具体投影／俯角、建造格尺度、自由旋转范围、纹理分辨率和模型预算。

建议初期固定主观察方向并支持平移与缩放；是否需要有限旋转通过相同场景试用决定。不再继承 32px 像素规范。

### 12.2 主工作区

场景是主要工作区；任务看板收纳在侧边；选中目标或对象时给就地操作和简要投入／效果信息。资源、运行速度与关键告警保持易达，历史和长文案按需展开。

选择目标与选择机器人是不同层次：前者回答“要完成什么”，后者回答“正在由谁完成、是否要干预”。不得让一次正常委托重新退化为逐台点名、逐单提交。

### 12.3 真实空间与工作表现

机器人实际移动，货物经历采出、运输、交付、加工等相关阶段。路径不可达必须影响执行，不能穿越不可通行物或瞬间到达。

首批先实现足以让这些动作可信的小范围空间关系，不同时承诺复杂拥堵、道路网络、电缆拓扑、多楼层与飞行物流。

建成、运转、缺电、维护、暂停的设施需要不同且可理解的表现。关闭台词后，玩家仍能看懂基地在做什么。

### 12.4 风格确认方法

在已确认的两款参考方向内，用同一镜头、同一内容与相同 UI 占位比较少量原创方案，不再反复让所有者在已淘汰的 A/B/C 间重选。优先级为：对象容易辨认 → 工作过程可理解 → 建成前后变化明显（包括地表）→ 材质与气氛更丰富。样张确认后制作一台机器人、两类设施和可改造地块，再冻结生产规范。见 [美术方向 v0.2](../art/art-direction.md)。

图像生成工具只用于开发期概念、参考和适当的纹理／UI 制作。真实三维模型、材质、动画与性能验证是另一段制作工作，不能把图片当作完成的三维资源。

### 12.5 地表记录建设历史（C15 已确认）

清理土坡、推平场地和矿点开挖应真实改变地表或场地几何及其外观，并持久保存。涉及碰撞、坡度、通行与建设有效性的部分必须一起更新；不能画面是平地，机器人却仍按旧坡走，也不能低画质关闭真实改造结果。

第一批建议采用小范围、可验证的分阶段形变或局部地块改造，不承诺整颗星球任意挖洞、地下洞穴或逐粒土壤物理。具体地形技术不在产品文档预定。灰模阶段就应证明改造、导航、任务和存档一致，避免最后贴图补救。

取消工程释放未执行任务，但已推平的地面和已采出的坑不会瞬间复原；恢复地形若以后提供，应成为独立操作。装饰履带印可压缩／淘汰，真实地形变化不能随视觉缓存消失。

## 13. 新档、时间和失败体验

建议保留“荒地到基地”的正式新档承诺：着陆器与必要自举物资存在，但主要永久设施由玩家建立。初始套件用于避免无法开始的死局，而非替玩家建好大半基地。

分阶段教学应让玩家逐渐学会“给目标、看计划、设边界、在变化时介入”，而不是教会一长串必须亲手重复的材料配方操作。

已确认：首阶段先建设成长，初期不强制用首夜危机推动体验。**本轮更新：基本耗电、耐久与维修不再整体后置，应与核心循环共存；环境复杂度与高压场景可以后续增加。**管理不当可能导致基地失去运转能力，但这不等于新手必须遭受一次损失。

单机暂停由明确状态控制；关闭游戏不补算离线收益。切换窗口是否自动暂停是设置问题，不再继承浏览器租约机制。

用户取消或调整目标是正常玩法，不应被教学惩罚。失败说明应指向可理解的原因与恢复途径；无法达成也可以是一次诚实结果。

### 13.1 经营失败不是脚本惩罚（C17 已确认；失败细则建议）

可能的危机链包括：扩张挤占维护物资 → 可用机器人减少 → 采集和供能恢复能力不足 → 无法继续维持生产。它来自真实规则，不来自模型随机出错或强制剧情。

保留可行的新手自举路径，并提供可理解的预警；不采用“无论怎样都会白送资源救回来”的隐藏保底。已告知风险且玩家仍选择冒险时允许后果出现，具体危险授权方式与数值尚需确认。

“暂时停机”“需要新条件”“还有恢复路径”“本次基地确实不可恢复”应区分。只有在已定义规则内能明确判定不可恢复时才显示失败；规划器搜索超时、模型答不出和未知矿源不是失败证明。自动存档保留可追溯节点；读旧档、重开或单独的援助模式是否影响成绩以后决定，不能把对玩家的损失强制升级成删档／永久死亡。

## 14. 首个可玩版本 G1：会把目标办成的工程队

### 14.1 目标

在 Mac 原生构建中，通过一段真实的缺料建设场景，让玩家体验目标受理、前置补齐、协作执行、地表改造、补能维修、建设成果与保存恢复。安全体验和风险分支分别验证，不要求每局损失。

G1 既不是只有 3D 画面的旧表单，也不是只有聪明清单、没有实际模拟的 agent 演示。

### 14.2 必须包含

| 交付项 | 完成含义 |
|---|---|
| 可操作的小型 3D 基地 | 指挥镜头、对象选择、真实移动、施工与运行状态 |
| 一处真实地表改造与一处开挖示例 | 推平／清场及开采留下变化，碰撞／通行／存档一致；不是贴花演示 |
| 一条补能与维护保障链 | 同一机器人在真实耗电／磨损后回充、维修并回到合法任务；无免费恢复 |
| 至少一个跨采集／加工／建设的目标 | 当前物资不足但路径可达时能自动完成前置链 |
| 可见的目标与任务看板 | 展示实际依赖、执行者、阻塞与变更 |
| 多台不同能力机器人 | 自动分工与至少一种真实协作／资源争用处理 |
| 玩家授权边界 | 预算、保护条件、超界请求、暂停／取消 |
| 至少一个变化场景 | 可达替代方案自动采用；超界方案请求玩家 |
| 本地能力候选的真实验证 | 不是只拿规则结果加一段模型点评冒充 AI 决策 |
| API 切换接入样例 | 本地与 API 共用任务语义；费用调用需单独授权 |
| 本地保存与读取 | 目标、进度、资源和已接受计划一致恢复 |
| 首轮联合性能记录 | 3D、地形变更／导航、模拟、推理与保存同时运行；包含较低配置探针 |

API 适配可以先通过模拟提供者验证故障分支，真实 API 能力未跑时必须标记 NOT_RUN。若 G1 收窄成仅一种提供者的试验版，要明确收窄，不能称“本地/API 均已通过”。

### 14.3 明确不包含

首期不做多人基地、玩家战斗、共享市场、无边界自然语言工具调用、全基地无限自定目标、复杂多层世界、大规模程序生成、强制联网账户系统及所有供应商的通用 API 兼容。不预先承诺任意体素挖掘、地下洞穴或整星球重塑；但不能以此删除已确认的小范围地表改造。

机器人长期性格成长、广泛社交对话、深层外部经济、大规模内容扩展可以后续讨论，但 AI 目标委托不能被整体移到“世界与共在”远期阶段。

### 14.4 内部验证顺序

先验证一个目标从命令到真实世界结果；再验证资源不足时的前置展开；然后加入一次变化与两目标竞争；最后联合本地推理、正式小样与保存测试。

这是同一短切片的实施检查点，不是要求先做一个完整系统才能第一次让所有者试玩。

### 15.1 如何证明不是写死的演示

除了固定的阵列场景，还需要留出的组合：不同物料缺口、不同队伍占用、已有在途产出、未授权前置、任务冲突、目标取消和故障恢复。至少一个不同的受支持建设目标也应走相同能力路径。

规划结果按执行后的世界目标判定，不按“看起来像计划”或文字流畅度判定。非法输出被拦下是可靠性结果，但不能据此算作目标成功完成。

### 15.2 真人签字

所有者可以随时停止试玩，不必为了配合验收坚持到时间目标。观察是否理解委托、愿意调整边界、能看到成果，以及是否主动提出下一个目标。

对“更想继续玩”的结论只归属于实际真人体验，不用多个 AI 代理投票替代。

## 16. Mac 参考设备与性能产品要求

参考设备已明确：**14 英寸 MacBook Pro，M3 Pro 满血配置，36GB 统一内存。** 后续不再把平台或设备视为未回答问题。最低配置、推荐配置和正式支持的 macOS 版本另需验证。

性能要求是游戏、模拟和 AI 的整体体验，而不是单独模型的生成速度：玩家操作不被推理锁住，重要进度稳定推进，读取保存不损坏计划，长时间运行不持续泄漏内存。

建议先以参考设备上 60fps 为画面目标，注明渲染分辨率、画质、机器人／设施／任务规模和倍速；这不是现有成绩。具体帧时间分位、内存预算、规划延迟和负载规模在技术验证中核定后进入 G1 合同。

同时记录：输入反馈延迟、从目标登记到第一份可执行计划的时延、首个机器人行动时间、模型等待／回退、模拟吞吐、帧时间峰值、总内存峰值、模型缓存、保存时间与连续运行稳定性。

1–2GB 可作为小文本能力的探索预算，不是整个 AI 系统的硬性上限，也不是模型文件大小等于运行内存。不得把 36GB 当作可被一个模型独占的资源。

本轮新增低配置要求：至少验证一个明显低于开发机的原生 Mac 档，8GB／16GB 候选设备用于发现边界，不提前宣布最低配置。画质降级可以减少装饰和视觉细节，不能删除地形事实、智能委托或机器人保障循环。详细门槛在 [技术验证计划](../engineering/technical-validation-plan.md) 中作为候选目标列出。

早期准备正常、后期候选和压力档，分别运行实际任务与推理。具体规模不依据空场景或纯渲染图标测试就宣布支持。

## 21. Codex 开发方式（工具已确认，工作方法为建议）

### 21.1 角色划分

Codex 是开发期执行工具：读取项目文档和文件、修改代码与配置、调用经授权的本地构建／测试工具、整理证据并提交可审查改动。Godot 是引擎、场景与预览工具；Blender 等是三维资源制作工具；本地分类器／语言模型是运行时 NPC 能力。不要混为一谈。

主工作流建议位于所有者的 Mac 本地环境，便于原生构建、图形与 Metal 实测。其他环境可以承担纯模拟测试，但不替代真实 Apple Silicon 客户端验收。[S9][S10]

### 21.2 对 Codex 友好的工程要求

不依赖聊天记忆或未记录的编辑器点击。产品、架构与美术规范使用 Markdown；模拟规则和数据格式明确；场景与资源具有稳定 ID；导入／测试／构建均有可重复入口。

`AGENTS.md` 只放当前入口、范围、命令、证据要求与禁止事项；历史报告另存。Codex 官方说明会读取并分层组合这类文件，不能留多个互相竞争的现役方向。[S11]

核心模拟、界面场景与 AI 适配分别有可检查边界。C# 为游戏主语言；若资源自动化使用 Python 或少量工具脚本，不能因此复制另一套运行时规则。

三维源资源与导出物分开：建议保留 Blender 源文件，游戏消费审核过的 glTF／GLB；绑定、材质、碰撞和导入结果要在 Godot 中确认。[S12] 大型二进制资源及权重的版本管理方式单独核定，不把全部模型权重直接塞进普通 Git 历史。

### 21.3 单个任务的交付闭环

受理一个受限任务 → 修改 → 编译与纯模拟测试 → Godot 导入／场景运行 → 实际画面与状态核对 → 交付可启动构建和证据 → 产品／审美判断。

Godot 提供命令行启动、指定场景、无窗口导出等能力。[S10] 这些能力使自动化可行，但本项目尚未实现所需脚本、画面采集和验收入口。

无窗口测试只证明对应的逻辑与导入／构建结果，不证明画面正确、操作可读、Metal 性能达标或游戏好玩。状态测试和画面测试都要保留；真人签字不可由“Codex 说已完成”代替。

每次交付至少记录：具体提交、启动方式、已跑命令与结果、未跑项、真实截图／运行记录、相关基准档。不把概念图当游戏截图，不把模板回退说成模型自主决策。

### 21.4 不变成提前建设一个开发平台

先落实最少的测试、启动与构建入口，足以完成第一个可玩目标；不先造万能编辑器自动化、复杂调度系统或插件集合。非必要的扩展工具不是开工前置。
